How OMG works

OMG exists to show how a language is put together, so nothing here is hidden. This page follows a program from text to output. The boxes are live: they run the real OMG compiler on whatever you type.

01Four steps

A computer cannot run emit 1 + 2 * 3 as it stands. It is only a row of characters. Getting from there to the number 7 on the screen takes four steps, each one simple on its own, each one handing a tidier form of the program to the next.

00 source

Text

emit 1 + 2 * 3
01 lexer

Tokens

EMIT NUM PLUS NUM STAR NUM
02 parser

Syntax tree

emit └ add ├ 1 └ mul ├ 2 └ 3
03 compiler

Bytecode

PushInt(1) PushInt(2) PushInt(3) Mul Add Emit
04 VM

Result

7

The first three steps together are what people mean by "the compiler". The last one is the virtual machine, or VM: a program that pretends to be a very simple computer. The rest of this page takes the steps one at a time.

02The lexer: characters to tokens

The lexer reads the source one character at a time and groups the characters into tokens: the words and symbols of the language. Each token has a kind, sometimes a value, and the line it came from.

Things to notice, and to try:

  • The comment, the spaces and the ;;;omg header are gone. The lexer throws away everything the later steps do not need.
  • alloc and emit get kinds of their own, because they are keywords. total is an ID, a name the program made up. Rename it and see.
  • The end of a line is a token too (NL). OMG has no semicolons, so a new line is what ends a statement.
  • The lexer knows nothing about grammar. Type + + alloc 3 and it will list the tokens without complaint. It only objects to characters it cannot make into a token at all. Try an @.

03The parser: tokens to a tree

A flat list of tokens does not say which operation happens first. The parser works that out and records the answer as a tree, called the abstract syntax tree or AST. An operation sits above the things it operates on.

Read the tree from the inside out. The mul of 2 and 3 is tucked inside the add, so it has to be worked out first. That is all operator precedence is: a rule the parser applies when it decides where to hang each node.

  • Change the line to emit (1 + 2) * 3. The brackets do not appear in the tree. They have done their job by putting add inside mul instead.
  • Each node is a small list: what it is, its parts, and a line number at the end. The line numbers are carried along so that an error message can say where things went wrong.
  • This is where grammar mistakes are caught. Delete the 3 and the parser reports a syntax error, because * needs something on its right.

OMG's parser is a recursive-descent parser. That means it is a set of ordinary functions, one for each piece of grammar (one for statements, one for expressions, one for function calls), which call each other the same way the grammar nests. It is the kind you can write by hand and read from top to bottom.

04The compiler: a tree to bytecode

A tree is easy to reason about but awkward to run. The compiler walks it and writes out a flat list of small instructions, called bytecode. The trick is the order of the walk: for each operation it first writes the code for the parts, then the instruction for the operation itself.

So 1 + 2 * 3 becomes: push 1, push 2, push 3, multiply, add. The operators come after their operands, and the multiply comes before the add, which is exactly the order the work has to happen in. Put brackets round 1 + 2 again and watch Add move ahead of Mul.

The whole instruction set is small, about fifty instructions. Most of them do one obvious thing: push a value, load or store a variable, do arithmetic, compare, jump, call, return.

05The virtual machine: running bytecode

The VM is a loop. It looks at the next instruction, does what it says, and moves on. Its working memory is a stack: a pile of values where you can only add to the top or take from the top. An instruction like Add takes the top two values off and puts their sum back.

    06Loops, functions and errors

    Bytecode has no loop or if. It has jumps: instructions that change which instruction comes next. A loop is a test, a jump out if the test fails, the body, and a jump back to the test.

    Find JumpIfFalse and Jump in the listing. The numbers in brackets are the positions they jump to. An if is the same shape without the jump back. Replace the loop with one and compare.

    Functions

    A function's instructions are placed after the main program, and a table records where each function starts. Call remembers where it came from, jumps to the function, and Ret jumps back with the result on the stack.

    Each call gets a frame: a private set of variables, so that the x of one call cannot disturb the x of another. Frames are also what a traceback prints when something fails. One more detail is worth seeing: when the last thing a function does is call another function, the compiler emits TailCall, which reuses the current frame instead of stacking a new one. Add the line proc twice(x) { return square(x) } at the top and look for it.

    Errors

    try compiles to SetupExcept, which tells the VM where to jump if anything goes wrong before the matching PopBlock. When an error is raised, the VM unwinds to that point and hands the message to the except block.

    07A compiler in its own language

    Here is the part that makes OMG more than an exercise. There are two compilers, and one of them is written in OMG.

    • The Rust compiler came first. A new language cannot compile itself on day one, because nothing yet exists to run it, so the first compiler has to be written in something else. This one, along with the VM, is the Rust program you get from cargo build.
    • The OMG compiler is the same lexer, parser and code generator, written again in OMG: about 2,700 lines in a single file, compiler.omg. It is an ordinary OMG program that reads source text and writes bytecode.

    When the Rust program is built, it uses the Rust compiler once, to compile compiler.omg into bytecode, and stores that bytecode inside itself. From then on, running omg hello.omg does this:

    1The VM runs the OMG compiler, which reads hello.omg and writes bytecode.
    ▼
    2The same VM then runs that bytecode. This is your program.

    So every program is compiled by a compiler written in the language being compiled. A language that can do this is called self-hosting.

    How do you know the two agree?

    Two compilers for one language is a risk: they could drift apart. OMG guards against that with a strict test. Both compilers are given the same source, and their outputs must be identical, byte for byte. The hardest input to get right is the compiler itself, so that is what the test uses: 

    omg --verify-self-hosted bootstrap/src/compiler.omg

    This compiles compiler.omg once with the Rust compiler and once with the OMG compiler, and compares the results. It is called a fixed-point check: a compiler, fed its own source, produces itself. It runs on every change to the repository. If the two ever disagree, one of them has a bug.

    There is a stronger version. OMG also has a second virtual machine, written in OMG (vm.omg). With it, the OMG compiler can run on the OMG VM, which itself runs on the Rust VM. That is three layers of interpretation, and the output still has to match: 

    omg --verify-omg-vm bootstrap/src/compiler.omg

    When that passes, every step that understands the language happened inside OMG. Rust is only the floor it stands on.

    08Native code and JavaScript

    A VM is the simplest way to run bytecode, not the only one. OMG has two backends that translate bytecode into another language instead, so that something faster can run it. Both are written in OMG.

    • The C backend turns a program's bytecode into C source. An ordinary C compiler then produces a small stand-alone executable, around 30 KB, that needs neither Rust nor the VM. On Linux and macOS the whole OMG toolchain can be built this way, after which it rebuilds itself with no Rust involved at all.
    • The JavaScript backend does the same job with JavaScript as the target, which is what lets OMG run in a web page.

    Both keep the shape of the bytecode: each instruction becomes a line or two that does the same thing to a stack. Here is what they produce. The output is long because it is complete, so scroll down to the numbered case lines and match them against the bytecode.

    09What runs on this site

    No server runs your code, and none of this site is a rewrite of OMG in JavaScript. The OMG compiler and the OMG VM, both written in OMG, were translated to JavaScript by the JavaScript backend. That single file is what your browser loads. When you press Run, the layers are:

    Your programtext in the editor
    ▼ compiled by
    The OMG compilerwritten in OMGcompiler.omg
    ▼ bytecode, run by
    The OMG virtual machinewritten in OMGvm.omg
    ▼ both translated ahead of time by
    The JavaScript backendwritten in OMGnative-js.omg
    ▼ and run by
    Your browserits JavaScript engine, in a background worker

    Interpreting bytecode with a VM that is itself translated code is not fast. The playground therefore offers a second engine. Switch it to JS and your program is compiled to bytecode, translated to JavaScript by the backend running in your browser, and run directly, with no VM in between. On a recursive function the difference is roughly a hundredfold. Both engines must give the same answers; only the route differs.
