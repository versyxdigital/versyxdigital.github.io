How languages get built, and why C is under most of them

Every programming language has the same problem to solve: a processor only understands numbers, and people do not want to write numbers. This page explains how languages solve it, why nearly all of them end up leaning on a fifty-year-old language called C, and what is different about the way OMG does it. You do not need to know how to program to follow it.

The short version.

  • A language is a translator. Something has to turn text a person can read into instructions a processor can run.
  • Writing the whole translator yourself takes years, so almost every language borrows parts, and the parts are nearly always written in C or its close relative C++.
  • C got that position by being in the right place first. Operating systems are written in it, so everything else has to speak to it.
  • OMG is a small hobby language that borrows nothing: its compiler, its machine-code generator and the support code its programs carry are all written in OMG. That is unusual, but it is not new. Go does the same thing at a far larger scale.

01What a processor understands

The processor in your computer does very simple things, very fast. Add two numbers. Copy a number from one place to another. Compare two numbers. Skip to a different instruction. Each instruction is itself stored as a number, so a program, as the processor sees it, is one long row of numbers. This is called machine code. Here is "put 2 somewhere, then add 3 to it" for the processor in most laptops: 

b8 02 00 00 00    # put 2 in a slot called eax
83 c0 03          # add 3 to that slot

Nobody wants to write that, and two more facts make it worse.

  • Processors disagree. The family in most laptops and desktops (called x86-64, made by Intel and AMD) and the family in phones and newer Macs (called ARM) use different numbers for the same jobs. Machine code for one is noise to the other.
  • A program never works alone. To show a letter on the screen or read a file, it has to ask the operating system: Windows, Linux, macOS. Each one has its own way of being asked.

So a programming language is a deal. You write something a person can read, and a tool turns it into what one particular processor and operating system can run. All the variety in how languages are built comes down to two questions: how does that tool work, and who wrote it?

02Three ways to run a program

Picture a recipe written in French, and a cook who reads only English. There are two obvious ways to get dinner made. Someone can stand in the kitchen and translate one line at a time, every time the dish is cooked. Or someone can translate the whole recipe onto paper once, and go home. Languages have the same choice, plus a popular third option that sits between the two.

An interpreter is the easiest to build and the nicest to use: change a line, run it again. It is also the slowest, because the reading and deciding happens afresh on every run, and again on every trip round a loop.

A compiler does the translating once. The file it writes runs on its own at the processor's full speed, and the person you give it to needs nothing else installed. The costs are that a compiler is much harder to write, and that the file only works on one kind of processor and one operating system.

A virtual machine, or VM, is the middle road and the most common one today. A small compiler turns the program into bytecode: instructions for a simple, made-up processor that does not exist. Then a program called a virtual machine plays the part of that processor. Bytecode is far quicker to run than raw text, and the same bytecode works anywhere the VM has been installed.

Fast VMs add one more trick. While the program runs, they watch for the parts that run most often and translate just those into real machine code on the spot. This is called just-in-time compilation, or JIT. It is why Java and JavaScript are much faster than a plain VM would be.

03Inside a compiler

A compiler is usually built as three parts in a row, like a factory line.

  • The front end understands the language. It reads the text, checks that it makes sense, and builds a tidy description of what the program means. It is different for every language.
  • The middle improves the program without changing what it does: removing work that is never used, doing sums ahead of time, rearranging loops. It works on an in-between form that belongs to neither the language nor the processor.
  • The backend turns that in-between form into machine code for one specific processor. It has to know every instruction that processor has, and exactly how each is written down as numbers.

The front end is the fun part, and the smallest. The backend is where the years go. A good one knows hundreds of instructions, decides which values get to live in the processor's handful of fast storage slots, and applies decades of collected tricks. And you need a separate backend for every family of processor you want to support.

The shortcut nearly everyone takes: LLVM

This is why most new languages do not write a backend at all. They use LLVM: a ready-made middle and backend that began as a university project in 2000 and is now kept up by Apple, Google and many others. A new language only has to produce LLVM's in-between form. LLVM does the rest, for every processor that matters.

There is an older shortcut too: have your compiler write out C, and let a C compiler finish the job. Every kind of computer has a C compiler, so your language runs everywhere at a stroke. OMG can do this, and it is how OMG reaches the systems its own backend does not cover.

04Linkers, runtimes and the operating system

Machine code is not yet a program you can double-click. Three more things stand between a compiler's output and something running on your screen.

The linker

Big programs are compiled in pieces, and they use ready-made pieces written by other people, called libraries. A linker glues the pieces into one file and fills in where everything ended up, so that one piece can find another. The finished file has a strict layout that the operating system insists on. Linux calls its layout ELF. Windows calls its one PE, and that is what a .exe file is. Most languages do not write their own linker. They use the one that comes with the system's C compiler.

The runtime

Every program carries helper code its author did not write: code to hand out memory and take it back, join pieces of text, grow a list, report an error. This is the language's runtime. In C it is small. In Go or Java it is large, and includes a garbage collector, which hunts for memory the program has stopped using so that it can be used again.

The operating system

A program cannot touch the disk, the screen or the network itself. It asks the core of the operating system, called the kernel, to do it. Each request is a system call. On most systems a program does not make system calls directly. It goes through a library the system provides, and that library was written in C, for C programs to use. It is called the C library, or libc for short. On Windows and macOS, going through the system's own libraries is the only route that is officially supported. Linux is the exception: its system calls are a documented, stable list that any program may use directly.

05Who compiles the compiler?

A compiler is a program. So it has to be written in some language, and then translated by some compiler. That looks like a chicken-and-egg problem. The way out is called bootstrapping, after the idea of lifting yourself by your own bootstraps.

  1. Write a first compiler for your new language in a language that already exists.
  2. Write a second compiler for your language, this time in your language.
  3. Use the first compiler to translate the second. You now have a compiler for your language, written in your language, that runs.
  4. From here on, each new version of the compiler is built by the one before it. The first compiler can be put away.

A language that compiles itself is called self-hosting. It is something of a rite of passage. A compiler is a large and fussy program, so being able to write one is good evidence that the language is fit for real work.

Most serious languages have done it. The big C compilers are written in C and C++, and compile themselves. Go's compiler was written in C until 2015, when it was translated into Go. Rust's first compiler was written in a language called OCaml. Follow any of these chains back far enough and it ends in the 1950s, with someone writing machine code by hand. OMG went the same way: its first compiler was written in Rust, and the How it works page tells that story.

Self-hosting means less than it sounds. Rust's compiler is written in Rust, but the machine code still comes from LLVM, which is C++. "The compiler is written in its own language" and "nothing else is involved" are two different claims. Section 07 shows which languages can make which.

06Why C is under everything

C was created by Dennis Ritchie at Bell Labs around 1972, for one job: writing an operating system called Unix. Until then, operating systems were written in assembly, which is machine code with names in place of the numbers, and is different for every processor. An operating system written that way is stuck on the machine it was written for.

In 1973 Unix was rewritten in C. That made it one of the first operating systems that could be moved to a different kind of computer: write a C compiler for the new machine, which is a small job by design, then translate Unix again and fix the few parts that really were tied to the hardware. Bell Labs' owner, the telephone company AT&T, was not allowed to sell software as a business, so Unix went out to universities for next to nothing, with its source code included. A generation of programmers learned Unix and C together, and took both with them into industry.

  1. 1957Fortran: the first widely used language with a compiler.
  2. 1969Unix begins at Bell Labs, written in assembly.
  3. 1972C.
  4. 1973Unix is rewritten in C, and starts to spread.
  5. 1985C++ goes on sale: C with a great deal added.
  6. 1989C becomes an official standard.
  7. 1991Linux, written in C. Python, whose interpreter is written in C.
  8. 1995Java and JavaScript, each run by a virtual machine written in C or C++.
  9. 2003The first release of LLVM, written in C++.
  10. 2009Go is announced. Its compiler is written in C.
  11. 2015Go's compiler is rewritten in Go. Rust 1.0 arrives, built on LLVM.

That history left C holding four positions that no other language has been able to take from it.

1. It is a thin layer over the machine

C has almost no runtime. A line of C becomes a handful of machine instructions that you could have predicted. That makes it fast, and it makes a C compiler small enough to be the first thing written for any new processor. A new chip gets a C compiler before it gets anything else.

2. The operating systems are written in it

The cores of Linux, Windows, macOS, Android and iOS are all written mostly in C, with some C++. (Linux has recently begun to accept a little Rust.) So the front door of every one of those systems is shaped for C programs to walk through.

3. Fifty years of libraries

A great deal of the software that everything else stands on is written in C, and has been hardened by decades of use:

SQLiteA database in a single file. It is inside every phone and every web browser.
OpenSSLThe encryption behind a large share of the web's padlocks.
zlibCompression: zip files, PNG images, web pages on their way to you.
FFmpegReads and writes nearly every kind of video and sound. It is inside browsers, media players and video sites.
curlFetches things over the network. It ships in cars, televisions and games consoles.

Nobody wants to write these again. A new language that could not use them would begin fifty years behind, so every new language makes sure that it can.

4. It is the common tongue

When one piece of machine code calls another, the two must agree on details at the level of the processor: where the inputs are put, where the answer comes back, how a group of values is laid out in memory. That agreement is called an ABI, short for application binary interface. Every operating system defines one, and defines it in terms of C. It has become the one thing every language agrees on. When Python uses a library written in Rust, or Swift uses one written in Go, both sides talk as if they were C. No C code needs to be involved, but C's rules are the meeting point.

What leaning on C looks like

Put the four together. The standard version of Python is a C program. The engines that run Java and JavaScript are C++ programs. Rust and Swift hand their machine code over to LLVM, which is C++, then to a linker from the C world, and the programs they produce call the C library while they run. A program can have no C at all in its own source and still have C under it, beside it and behind it.

The price

C trusts the programmer completely. It does not check that a program stays inside the memory it asked for, and mistakes of that kind are the biggest single source of serious security holes. Microsoft, and the Chrome team at Google, have each reported that about 70% of their serious security bugs come from this one family of mistake in C and C++ code. Newer languages such as Rust and Go exist largely to put a stop to it. But they still have to live in a world that was built in C, and that is why the dependence lasts.

Some notes, because a table this small has to round things off.

  • Each row is the usual version of the language: the standard Python from python.org, the V8 engine that runs JavaScript in Chrome and Node, the HotSpot virtual machine for Java. Other versions exist and make other choices.
  • Python makes no machine code of its own. Its interpreter is a C program, so the machine code that actually runs was made by a C compiler, long before your program existed.
  • On Windows and macOS, every language reaches the system through libraries the system provides, Go and OMG included, because that is the only supported way in. The last column is about Linux, where there is a choice.

  • Go is not alone at the bottom of the table either. OCaml, Free Pascal and D also make their own machine code. Seven rows cannot hold everybody.

09Where OMG fits

OMG is a hobby language, made by one person to learn how all of the above works. It has nothing that a professional language lacks, and it lacks a great deal that they have. What it does have is a complete toolchain with no borrowed parts, small enough to read.

How fast is the result?

One small test, the same in every language: work out the 35th Fibonacci number the slow way, which takes about thirty million function calls. Times are in seconds, on one machine.

Do not read much into this. It is one tiny program that measures one thing, calling functions and adding small numbers, and that happens to be what OMG's backend handles best. The Java and JavaScript times include starting their virtual machines. Run on OMG's own VM instead of being built, the same program takes 36 seconds: the VM is there for convenience, not speed. And the next section shows a job where OMG is far behind.

10The test: a video player

"No C anywhere" is an easy thing to say about hello world. The real test is a job that everybody uses C for, and playing video is that job. Nearly every player in the world hands the work to FFmpeg, from section 06, or to a special chip.

So OMG has a video player, and every part of it is OMG. It opens an MP4 file, unpacks it, decodes the video (the format is called H.264, and it is what most video on the web uses), and puts the pictures in a window. The decoder is about 6,300 lines. The window is opened by OMG's runtime talking to the system directly. The whole player is a single file of under 1 MB, for Linux or Windows.

Is it right?

H.264 has a useful property: decoding is exact. Every correct decoder must produce precisely the same pictures, down to the last dot. So the referee is FFmpeg itself. Over sixty test clips went through both, including real files from the web, and every picture OMG produced matched FFmpeg's bit for bit.

Is it fast?

No. To play smoothly at 30 pictures a second, a player has 33 thousandths of a second for each one. Here is how long OMG takes, on one processor core:

FFmpeg decodes the same files 20 to 40 times faster, because its busiest loops were written by hand, instruction by instruction, over twenty years. There is also no sound yet.

Both halves of that are the point. A small language with nothing underneath it can do a job this demanding, and get every bit right. And the fifty years of work inside the C libraries are real, and not something a hobby project catches up with.

11What OMG is not

  • It is not the first to do this, or the best at it. Go has always had its own compiler, backend, linker and runtime, all of them written in Go since 2015. It covers a dozen kinds of processor, and a good part of the internet's plumbing runs on it. OMG covers one family of processor on two systems.
  • It is not free of C everywhere. On macOS, and on ARM processors, OMG still writes C and borrows a C compiler.
  • It does not escape the system. On Windows an OMG program calls Windows' own libraries, as every program must. And the operating system underneath is still written in C.
  • It does not make fast code. Its backend does almost none of the improving that LLVM or a C compiler does. Simple programs come out respectably quick; heavy number-crunching, like the video decoder, does not.
  • It did not come from nowhere. The first OMG compiler was written in Rust. And the playground on this site runs OMG inside your browser's JavaScript engine, which is C++.
  • It is not for serious work. There is one author, no ecosystem of libraries, and plenty that bigger languages take for granted is missing.

What it is: the whole journey from section 01 to section 04 in about 20,000 lines that one person can read from end to end. The well-known toolchains are too large for that. LLVM alone is millions of lines. If you want to see how a compiler, a backend, an executable file and a runtime actually fit together, small is the feature.
